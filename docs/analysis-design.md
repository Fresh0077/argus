## 分析分层

一次扫描里，代码会经过三层分析。三层解决的是不同的问题，产出的东西也**不是一回事**：

| 层 | 代码位置 | 产出 | 上限等级 | 回答的问题 |
|---|---|---|---|---|
| 语言识别 | `analyzers/detector.py` | `detected_language` | — | 这段代码是什么语言？ |
| 特征与候选线索 | `analyzers/clues.py` | `source=heuristic` 的发现 | `low` | 哪些位置值得人看一眼？ |
| 规则检测 | `analyzers/rules/` | `source=static_rule` 的发现 | `high` | 哪些位置符合某个已知的危险写法？ |

**线索层刻意更粗、规则层刻意更准**，这不是实现不彻底，而是分工：

- 线索层宁滥勿缺，用一条 SQL 关键字加拼接算子就能把位置挑出来，
  因此它需要人会读"疑似"两个字；
- 规则层每条规则都写明触发条件与修复建议，能给出 `rule_id`，
  因此它可以承担"这一处是什么问题、怎么改"。

两层都产不出"已确认的漏洞"。**单条正则命中的是候选发现**，不是结论。

### 为什么线索层仍然保留

规则命中所在的 `(行, 漏洞类别)` 上，启发式线索会被压掉（见[去重策略](#去重策略)），
但线索层不会因此变成死代码——它还在负责两类信息：

1. **来源标记**（`untrusted_input_source`）。这不是缺陷，而是"数据从这里进来"，
   和危险位置对照着看才有意义。规则层不做这种标注，因为它不产生"问题"。
2. **规则尚未覆盖的写法**。规则表是按语言逐条手工登记的，总有没写到的地方；
   线索层按语法特征匹配，覆盖面更宽。

## 一条发现的产生过程

规则检测对源码**逐行**执行，每一条规则对同一行做四步判断，任何一步不成立就放弃这一行：

```
定位    pattern 命中危险位置           →  这一行有那个调用/写法吗？
排除    exclude 未命中                →  它是不是已经转义过了？
值      dynamic_value_at 取到的那段是动态的  →  喂给它的是写死的常量吗？
触发    require / require_taint 至少满足一个  →  还有别的证据支持这是个问题吗？
```

四步的顺序是有意为之。**"值是不是常量"排在"触发条件"之前**，是因为它更硬：
`cursor.execute("SELECT 1")` 不管上下文如何都不该报；先排除掉它，
后面几步才有意义。

`dynamic_value_at` 决定"取哪一段值来问是不是常量"，四种取值对应四类危险位置：

| 取值 | 含义 | 谁在用 |
|---|---|---|
| `none` | 不取值，位置本身已经说明问题 | `eval`、`unserialize`、`v-html`、`\| safe` |
| `first_argument` | 只看第一个实参 | SQL（第二个实参是绑定参数，正是安全写法）、命令执行 |
| `all_arguments` | 任一实参动态就算 | `subprocess`、`document.write`、变长参数 |
| `assigned_value` | 取赋值号右侧 | `innerHTML =` 这类 DOM 写入 |

切分实参时必须处理引号、嵌套括号与顶层逗号——用正则做这件事会在
`execute("a, b", (x,))` 这类输入上切错位置，因此 `rules/values.py` 里是
一个带引号感知的小扫描器，而不是一条正则。

**行号只报告真正匹配到的那一行**，不推测、不模糊定位。因此规则层不存在
"未能可靠定位"的发现——它要么给出准确行号，要么不报告。

## 规则覆盖

共 22 条规则，按漏洞类别分组。**"适用语言"一列是规则登记的匹配范围**，
不是"该语言只查这类问题"。

### SQL 注入（1 条）

| 规则 ID | 说明 | 适用语言 | 触发档位 | CWE |
|---|---|---|---|---|
| `ARGUS-SQL-001` | 语句由外部输入动态构造后交给数据库执行 | Python, JS, TS, Vue, PHP, Java, Go, Ruby | 需附加证据 | CWE-89 |

只在**第一个实参**（查询语句本身）不是常量时报。这一条设计决定覆盖了本层
最重要的一个误报源：`execute("... = %s", (uid,))` 里的 `uid` 出现在第二个实参，
是绑定参数，把它算进"动态值"就会把参数化查询判成注入。

### 命令执行（8 条）

| 规则 ID | 说明 | 适用语言 | 触发档位 | CWE |
|---|---|---|---|---|
| `ARGUS-CMD-001` | 系统命令由外部输入动态构造后交给 shell 执行 | Python | 需附加证据 | CWE-78 |
| `ARGUS-CMD-002` | `subprocess` 启用 shell 解释且命令含动态内容 | Python | 需附加证据 | CWE-78 |
| `ARGUS-CMD-003` | PHP 命令执行函数收到动态内容 | PHP | 需附加证据 | CWE-78 |
| `ARGUS-CMD-004` | Node.js 子进程调用收到动态内容 | JS, TS, Vue | 需附加证据 | CWE-78 |
| `ARGUS-CMD-005` | Java 进程调用收到动态内容 | Java | 需附加证据 | CWE-78 |
| `ARGUS-CMD-006` | Go 命令名由外部输入决定 | Go | 需附加证据 | CWE-78 |
| `ARGUS-CMD-007` | Ruby 命令执行收到动态内容 | Ruby | 需附加证据 | CWE-78 |
| `ARGUS-CMD-008` | Ruby 反引号或 `%x{}` 中含插值 | Ruby | 需附加证据 | CWE-78 |

## 触发条件的两个档位

这是规则表里最重要的约定，它决定了误报率：

**第一档：位置本身即危险。** `eval`、`unserialize`、`v-html`、`| safe` 这类写法
出现在代码里就值得看一眼——它们几乎没有"正常且无害"的用法。命中即报告。

**第二档：位置本身常见且多数无害。** `innerHTML =`、`execute(`、`system(`
在真实代码里大量出现且多数没问题。这类必须再拿到证据才报告，证据有两种：

- **值不是写死的**（`dynamic_value_at` 那一步），或
- **能追到来源**（`require_taint` 那一步）。

两条路径是**"或"**的关系，同时给出时满足任一即触发。SQL 规则正是靠这个组合
覆盖两种写法：同行拼接（`require` 命中）、以及语句在前几行拼好、
这一行只负责执行（`require_taint` 命中）。

## 安全写法的排除

`exclude` 表达的是"这是安全写法，不要报"。它只列**明确的**函数名：

```
HTML 转义   escapeHtml / htmlspecialchars / DOMPurify.sanitize / html.escape …
shell 转义  shlex.quote / escapeshellarg / Shellwords.escape / Process.escape …
```

刻意不含 `escape(`、`e(` 这类通用短名——它们会误命中，**把真正危险的位置
一起放过去，比不排除更糟**。

反过来也要说清楚：命中 `exclude` 只表示"这一行有转义动作"，
**不等于已经安全**。转义是否正确取决于它针对的语境（HTML 正文、属性、
URL、JavaScript 各需各的转义方式），那超出了正则能判断的范围。
因此本层选择"看到明确的转义函数就放过"，接受由此带来的漏报。

## 来源跟踪及其边界

`analyzers/taint.py` 做一件很小的事：记下"哪些变量的值来自不可信输入"，
以及这件事发生在第几行。规则据此把

```
危险位置 + 来源可追溯   →  high
危险位置 + 来源不明     →  medium
```

区分开。它**不是数据流分析**，边界如下（这些是设计约束，不是待办事项）：

| 不做 | 后果 |
|---|---|
| 不跨函数 | 函数参数、返回值、跨文件引用都不追踪；参数在函数体内就是普通变量 |
| 不处理别名与容器 | `a = b` 会传播，但 `d["k"] = b` 之后通过 `d["k"]` 读取不识别 |
| 不识别净化 | `uid = int(uid)` 之后仍算不可信，是否安全交给规则的 `exclude` 判断 |
| 不区分作用域 | 同名变量在不同函数里会互相干扰 |
| 不区分加法与拼接 | `i + j` 会被当成拼接（见下） |

### 内联来源

除了变量，来源表达式**直接写在危险位置上**的情况也识别：

```php
system($_GET["cmd"]);     // 没有中间变量，变量表里查不到，但它显然更明确
```

这与变量跟踪一样不是数据流分析——它只回答"这个位置上的文本本身是不是外部输入"。
两者的判断口径共用同一份模式表，因此不会出现"来源标记说是、来源跟踪说不是"。

### 安全性质

错判的**唯一**后果是等级与置信度偏高，**不会凭空产生发现**——
发现的有无始终由规则模式决定。唯一的例外需要说明：SQL 规则的 `require_taint`
本身就是触发条件之一，因此把一个本不该标记的变量标成"拼接构造"，
理论上会让一条 SQL 发现多出来。可及的情况是算术表达式（`total = i + j`
之后的 `cursor.execute(total)`），这类代码本身已经很不寻常。

## 去重策略

**以 `(漏洞类别, 行号)` 为唯一键**，同一行同一类别只产出一条发现。因此：

- 一条规则在同一行匹配到多处（一行里调了两次 `os.system`）只报一次；
- 同类别的两条规则同时命中同一行时，按规则表声明顺序取第一条
  （因此更具体的规则必须写在更宽泛的规则之前）；
- 启发式线索在与规则命中相同的 `(行, 类别)` 上不再输出——两者说的是同一件事，
  而规则给出的是同一个结论加上规则 ID、触发条件和针对性建议，信息量严格更大。
  未被规则覆盖的线索照常输出。

选 `(类别, 行号)` 而不是 `(规则, 行号)`，是因为使用者关心的是
"这一行有一个 SQL 注入问题"，而不是"有两套正则都想说这一行有问题"。

### 发现 ID 的稳定性

`id` 是 `(来源, 规则 ID, 起止行, 证据)` 的 SHA-256 前 16 位，
**刻意不含 `severity` 与 `confidence`**——否则调整一次等级，
同一处代码在界面上就会变成一条"新发现"，历史与去重都无从谈起。

## 等级与置信度

- **规则层等级上限是 `high`，且只在确认到来源时给出。** 没有来源证据时是 `medium`。
  单条正则够不上 `critical` 所暗示的"已确认且后果严重"，规则层不用这个等级。
- **`confidence` 是规则自身的确定性估计，不是漏洞真实发生的概率。**
  它随"是否确认到来源"变化，两个数字都由规则表写死，不是算出来的。
- `analyzer_status[].findings_count` 统计的是**最终响应里保留下来**的发现数量，
  各分析器的数量之和等于 `summary.total_findings`，不会让人觉得有发现丢失了。
- 不同分析器的 `confidence` **不相加**，也不合成"总体安全分数"。

## 已知的误报来源

按影响从大到小：

1. **跨行的写法看不到。** 逐行匹配，因此 `cursor.execute(` 与它的实参
   分处两行时，取不到值，规则会安静地不报。这是漏报；但反过来，
   一行里写了两个语句时（少见但合法），后半句的来源会被算到前半句头上，
   这是误报。
2. **字符串拼接与算术加法分不清。** `q = a + b` 被当作"拼出来的字符串"。
   不引入类型信息就分不开，而做类型推断超出了本层定位。
3. **整行注释会跳过，行内注释不会。** 以 `#`、`//`、`*`、`/*`、`<!--`
   开头的整行会被跳过（注释里举例说明"不要这样写 `eval(x)`"是极常见的写法）。
   但 `eval(x)  # 这里来自 request.args` 这种**行尾注释**仍会被读进来：
   行内截断不能用 `//`，它在 Python 里是整除运算符，按它截断会把
   `execute(sql + a // b)` 的后半行吃掉。
4. **变量名撞车。** 不区分作用域，另一个函数里同名的变量会把无关位置
   判成"来源可追溯"，从而把等级从 `medium` 抬到 `high`。等级偏高而结论不错，
   但会让人以为证据比实际更硬。
5. **`exclude` 是行级的。** 同一行里既调了转义函数、又拼接了未转义的内容时
   （`f(escapeHtml(a), b)`），整行会被放过。
6. **框架与包装函数不认识。** 自研的 `safeQuery()`、`myEscape()` 不在
   `exclude` 列表里，会被照常报告（这是可以接受的误报方向：
   宁可让人判一次"这是我们的安全封装"）。

## 已知的漏报来源

1. **跨行书写的语句**（见上）。
2. **没有登记的语言。** `rules_for_language` 返回空，此时 `rules` 报 `success`
   而发现为 0。这种情况在界面上与"查过没问题"很难区分，因此
   [api.md](api.md) 要求前端必须结合 `analyzer_status` 展示。
   当前上传白名单里的每种语言都有规则，所以它只在用 `language` 参数
   传入白名单之外的语言时出现。
3. **自研的封装与框架 DSL。** 规则匹配的是标准库与常见框架的写法。
4. **净化是不是真的到位。** 看到明确的转义函数就放过——转义对不对、
   语境对不对，正则判断不了。
5. **`critical` 级别的问题。** 规则层不产出这个等级，因此不要期望它
   帮你区分"严重但需人工确认"和"极其严重"。

## 与其他分析器的关系

规则检测器是一个**独立的接口**，不依赖 FastAPI、不读写文件、
不知道 Semgrep 或 LLM 是否存在：

```
detect_rule_findings(source_code, language) -> RuleDetectionOutcome
```

输入是源码与语言，输出是一批 `Finding` 外加一个可选的 `skip_reason`。
后续接入其他分析器时，只需要在编排层把各自的结果并起来。

需要留意的两点：

- **Semgrep 与 LLM 的合并逻辑不在这里。** 它们的环境依赖与降级路径
  （CLI 是否安装、API key 是否配置、超时、限流）和规则层完全不同，
  那属于多分析器整合要单独处理的问题。
- **`rule_id` 只由规则类分析器填写。** 启发式线索不是规则，
  这个字段为 `null`；将来 Semgrep 会填它自己的规则标识。
